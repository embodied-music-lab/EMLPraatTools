EML Stats & Graphs — independent verification

Two paths,
one number

Run the same dataset through the Praat plugin and through R. Put the two outputs side by side. Then tell us where we are wrong.

For Josh Gilbert Requires R, and Praat 6.6.30 or later No R packages needed

This walkthrough asks you to check the plugin's arithmetic yourself, without taking anyone's word for it. Each of the six analyses below has a committed dataset, an exact route through the Praat interface, and a base-R script that computes the same quantities. You run both. You compare.

Every step here was driven and confirmed on 26 August 2026 against Praat 6.6.30 — the menu commands exist, the dialog fields carry the labels named, and all six R scripts run clean from the repository root. Where something could not be verified without a live interface, it says so.

The last section is the part that matters most, and it is the reason for the meeting: once you have run this, we want you to break it.

Before you start

Four steps. Praat loads plugins only at launch, so the restart is not optional.

  1. Clone the repository. Everything below runs from its root directory.

    git clone https://github.com/embodied-music-lab/EMLPraatTools
cd EMLPraatTools

  2. Download plugin_EML_StatsGraphs.zip from the GitHub Releases page and unzip it. Do not rename the folder. Praat identifies the plugin by that exact name and a script has no way to ask what folder it lives in, so the name is hardcoded throughout.

  3. Drag the whole plugin_EML_StatsGraphs folder into your Praat preferences directory. On macOS that is ~/Library/Preferences/Praat Prefs/.

  4. Quit Praat completely and reopen it. The Objects window should now show New > EML Stats & Graphs, and selecting a Table should reveal buttons beginning EML: down the right-hand side.

    Below Praat 6.6.30 the plugin refuses to load and says so — no menu items appear at all, rather than a partial install that fails later inside an analysis.

Reading a CSV into Praat

Use Open > Read Table from comma-separated file... The resulting Table object takes its name from the file with the extension dropped, so v08_twogroup_input.csv becomes a Table called v08_twogroup_input.

The obvious command is the wrong one. Plain Open > Read from file... — the entry that looks like "just open my file" — rejects a CSV outright with File not recognized. It fails loudly rather than mis-parsing, but it is the first thing most people try.

Saving what Praat prints

Click the Info window to bring it forward, then File > Save as... That window is a stock Praat text editor, so this is Praat's own behaviour rather than anything the plugin adds. This is the one step in the walkthrough that could not be driven headless for confirmation.

Where a difference is not an error

  • The plugin prints p < .001. R gives you 6.04e-07. That is an APA display floor, not a disagreement — the plugin also prints the exact tail in parentheses.
  • Rank-biserial r uses the directed form (U1 − U2) / (n1 · n2), positive when the first group exceeds the second. The competing textbook convention flips the sign. If you prefer the other one, say so — it is a choice we made, not a result.
  • Cohen's d and Hedges' g are two different correct effect sizes and will not equal each other.

Where a difference is not an error

  • R's TukeyHSD prints the difference as row minus reference, so its Mezzo-Soprano is −5.5295. The plugin prints the opposite subtraction order, Soprano − Mezzo = 5.5295. Compare magnitudes and interval widths, not signs line for line.
  • The plugin rounds each cell of the sums-of-squares table independently before printing, so the printed rows will not add up to the printed total beyond about two decimals. The underlying values do.

Where a difference is not an error

  • Dunn's test has no canonical base-R function. The R script here implements Dunn (1964) with tie correction, matching what scikit-posthocs produces. Reach for PMCMRplus or the dunn.test package instead and the numbers may shift, because those packages make different default choices about ties and adjustment. Agreement with this script is the meaningful check.
  • Epsilon-squared sits in the same position — a defensible convention rather than a single settled standard.

Where a difference is not an error

  • Kendall's W of exactly 1 is not a bug. This fixture was built with perfect agreement across singers, which is why the rank sums are exactly 20, 40 and 60.
  • All three Friedman post-hoc raw p-values are identical here, so Holm must give all three the same adjusted value. That is Holm's monotonicity working, not a collision.
  • The plugin prints its exact tail to three significant figures beside the floored p. Expect that tail to round-trip to three figures, not to full double precision.

Where a difference is not an error

  • This is the one to look at hardest. The plugin's Spearman t and df are the large-sample approximation t = rho · sqrt((n−2)/(1−rho²)), printed so the row lines up visually with the Pearson row above it. They are not exact.
  • This dataset contains ties, so cor.test falls back to the same approximation and the two agree to displayed precision. On a tie-free dataset they need not agree, because cor.test would then use an exact permutation p. Compare rho and its p against cor.test; treat the Spearman t and df as a display convenience.

Where a difference is not an error

  • The plugin's R is signed to match the slope. Base R never exposes a signed R — only R², which is unsigned by construction. Take sqrt(r.squared) naively on a negative-slope dataset and you will get the wrong sign. evidence/csv/v13_regression_neg_input.csv exists to test exactly this.
  • A free consistency check that needs no Praat output at all: in simple regression F equals the slope's t squared. 9.904² ≈ 98.09.

Checking our answer against ours

Two further things you can run without any of the above.

Each of the six analyses has a committed capture of what Praat printed when it was last driven — evidence/info/v08_twogroup_info.txt and its siblings. Your own Info window output should match those numerically. Where the wording of the explanatory text differs, that is annotation drift, not arithmetic; compare the numbers.

The whole suite also runs in one command:

Rscript validate/run_all.R

It expects to end 0 FAILED and exit 0. If a run cannot complete it says so in a banner and exits 2 rather than 1, because "the suite ran and something failed" and "the suite never ran" need to be different answers — a log of a run that checked nothing otherwise looks exactly like a clean one.

What we are actually asking

The comparison above is the warm-up. This is the request.

Propose datasets that would break it

Every fixture in that table was written by the people who wrote the code, which is the structural weakness of the whole exercise. We chose the cases; we cannot choose the ones we failed to think of. Send data — real or constructed — that you would expect to be handled badly. Degenerate groups, heavy ties, single-observation cells, extreme scales, missing values in awkward places, anything where two defensible conventions diverge.

Revise the R where you would have written it differently

The six scripts in walkthrough/r/ are the oracle. If the oracle is wrong, agreement between the two sides means nothing. Where a script leans on a convention you would not have chosen — Dunn's tie correction, the rank-biserial sign, the Spearman approximation — say so, and say what you would use instead.

Tell us what an independent reviewer would still not accept

The claim we can make today is that each procedure computes what it says, checked against R, with a re-runnable suite as the warrant, scoped to the scripting interface. The claim we cannot yet make is that every route through the interface reaches every procedure identically. If there is a third claim you think a methods reviewer will demand, better to hear it now than in review.

Why this is a contribution and not a favour

A validation paper written entirely by the authors of the thing being validated has a hole in the middle of it. The fixtures, the oracles and the tolerances were all chosen by the same people who chose the algorithms, and no amount of internal rigour closes that gap.

Independent test cases and an audit of the R side close it. That is a methods contribution with a name on it, not a courtesy read — and it is the half of the argument we cannot supply ourselves.
